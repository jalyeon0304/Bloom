# 급전지시 모니터링: 웹 vs 앱, 기술스택 의사결정

## 결론(권장)
- **1차 MVP는 웹 기반(사내망 내부 접속)으로 시작**하는 것이 가장 유리합니다.
- 크롤링은 **Selenium보다 Playwright 권장**입니다.
- 권장 스택: **Python + Playwright + FastAPI + PostgreSQL + React(또는 서버 템플릿 UI)**

---

## 왜 웹이 더 유리한가?
요구사항 기준:
- 여러 사용자가 같은 화면에서 **감발 진행도 / 현재 TMO / 이력**을 동시에 확인
- 기록물(**CSV/Excel**) 다운로드
- 향후 지속적인 기능 추가 및 버전 업데이트 필요

### 웹의 장점
1. **배포/업데이트가 가장 쉽다**
   - 서버 한 번 배포하면 모든 사용자가 즉시 최신 버전 사용
   - 프로그램 재설치/업데이트 안내 부담이 적음
2. **여러 사용자 동시 사용에 강함**
   - 권한관리(조회/관리), 접속 로그, 감사 이력 등을 확장하기 쉬움
3. **데이터 내보내기(CSV/XLSX)가 자연스럽다**
   - API에서 바로 생성 후 다운로드 제공 가능
4. **운영 자동화에 유리**
   - 수집 스케줄링, 장애 알림, 백업 등 서버 중심 관리 가능

### 앱/설치형 프로그램이 나은 경우
- 외부망 단절 환경에서 오프라인 사용이 핵심
- PC별 로컬 장비 연동이 필수
- UI 성능 요구가 특수하고 데스크톱 네이티브 기능이 중요한 경우

대부분의 "사내 포털 + 다수 사용자 + 지속 배포" 시나리오는 웹이 더 유지보수 비용이 낮습니다.

## Selenium vs Playwright

## Playwright 권장 이유
1. **현대 웹 대응력**
   - 동적 렌더링, 비동기 UI에서 안정적인 대기/셀렉터 동작
2. **자동 대기(auto-wait) 기본 제공**
   - Selenium 대비 플래키 테스트/크롤링 이슈가 적은 편
3. **코드 가독성과 유지보수성**
   - 로그인/탭 이동/테이블 파싱 흐름을 비교적 명확하게 작성 가능
4. **헤드리스 운영과 디버깅 편의**
   - 스크린샷, 트레이스, 네트워크 추적 지원

## Selenium을 고려할 수 있는 경우
- 사내 표준이 Selenium으로 이미 고정되어 있고, 운영 자산(드라이버 배포/공통 유틸)이 있는 경우
- 특정 레거시 브라우저/정책 때문에 Selenium만 허용되는 경우

**정리:** 신규 구축이고 선택권이 있다면 Playwright를 우선 추천.

## 추천 구현 구조 (운영 관점)
1. **Collector Worker (Python/Playwright)**
   - VPN 연결 가능한 서버에서 Webview 접속
   - `[급전지시]` 이벤트 감지 및 발전량 수집
2. **API Server (FastAPI)**
   - 현재 상태, 진행도, TMO, 이력 조회 API
   - CSV/XLSX 다운로드 API
3. **DB (PostgreSQL)**
   - 이벤트/측정치/수집로그 저장
4. **Web UI**
   - 대시보드(현재 상황), 이벤트 타임라인, 다운로드 화면

---

## 초기 MVP 범위(2~3주)
- 실시간(예: 1분 주기) 수집
- 최근 급전지시 현황 + 현재 발전량 대시보드
- 기간별 이력 조회
- CSV 다운로드 우선 제공, XLSX는 2차 확장
