# VPN 전략 의사결정: 중앙 승인형 vs 사용자 개별 VPN 필수

질문: "이 변경사항(중앙 승인형)을 적용할지, 모든 사용자가 본인 사내 VPN 환경에서만 쓰게 할지"

## 결론 (권장)
- **초기 운영은 하이브리드가 가장 현실적**입니다.
  1. 기본 정책: 가능한 사용자는 사내 VPN 환경에서 사용
  2. 예외 정책: VPN 불가 사용자/모바일은 **중앙 승인형**으로 제한적 허용

즉, 둘 중 하나만 고집하기보다 **보안과 사용성 균형**으로 가는 것이 좋습니다.

## 옵션 비교

### A) 모든 사용자가 각자 VPN 필수
장점
- 보안 모델이 단순함 (내부망 정책 그대로)
- 중앙 서버 인증/승인 로직 부담이 적음

단점
- 모바일/외부 협업 환경에서 사용성 저하
- 사용자별 VPN 장애가 곧 서비스 장애로 이어짐
- 운영팀이 사용자별 접속 이슈를 계속 처리해야 함

### B) 중앙 승인형(현재 제안)
장점
- 사용자 단말은 VPN 없이도 데이터 조회 가능
- 크롤링/수집은 중앙 서버에서 일원화되어 운영이 쉬움
- 휴대폰/태블릿에서도 대시보드 접근성이 높음

단점
- 인증/권한/감사로그를 제대로 구현해야 함
- 중앙 서버가 단일 장애점(SPOF)이 될 수 있음
- 보안 통제(토큰 수명/기기 바인딩/승인 정책)가 필요

## 추천 운영 정책 (실무형)
1. **중앙 서버는 사내망/VPN 가능한 위치에만 배치**
2. **사용자는 Webview 직접 접속 금지**, 중앙 API/UI만 사용
3. **승인형 로그인은 고위험 계정 제외 + 짧은 토큰 TTL(예: 8시간 이하)**
4. **승인 로그/접속 로그/다운로드 로그 필수 저장**
5. **권한 분리**
   - 조회 전용 사용자
   - 승인 가능 운영자
   - 시스템 관리자
6. **긴급 차단 스위치**
   - 유출 의심 시 토큰 일괄 폐기

## 언제 어떤 선택이 맞나?
- 사용자 대부분이 사내 PC에서만 사용하고 모바일 필요가 거의 없으면
  -> **A(개별 VPN 필수)**
- 현장/이동 사용자, 휴대폰 조회, 빠른 전사 확산이 중요하면
  -> **B(중앙 승인형)**
- 현재 질문의 맥락(휴대폰/다른 환경 사용 요구)에서는
  -> **B 또는 하이브리드가 더 적합**

## 지금 코드 기준 판단
- 이미 승인형 흐름 데모 API가 있으므로, 버리지 말고 **운영 보안 강화 후 적용**이 효율적입니다.
- 단, 인메모리 저장소는 데모이므로 운영 전 반드시 DB/Redis/JWT/TLS/감사로그로 전환해야 합니다.
